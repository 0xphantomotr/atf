# `/prompt` Command Implementation Plan

Last updated: 2026-06-28

## 1. Objective

Add a conversational Telegram entry point that lets a user operate the existing ATF
platform with natural-language Albanian instructions. The command must orchestrate the
current project, upload, analysis, generation, status and report services without
replacing their deterministic authorization, validation or evidence controls.

The primary target flow is a ZIP attachment with a caption such as:

```text
/prompt Krijo projektin "Test Dosja Teknike", zgjidhe si aktiv, analizo dosjen,
gjenero Akt Kolaudimi dhe ma dergo PDF-ne.
```

The system should create and select the project, import the attached technical folder,
wait for parsing, request confirmation after showing the generation estimate, execute
the existing LangGraph workflow and deliver the resulting Akt Kolaudimi automatically.

The second target flow is project-grounded conversation:

```text
/prompt Kush eshte sipermarresi dhe ne cilat dokumente rezulton?
```

Answers must use only the active project's current evidence and must cite the source
documents in the Telegram response.

## 2. Product Principles

- `/prompt` is an orchestrator over existing services, not a replacement for them.
- The LLM proposes a structured plan; deterministic application code authorizes and
  executes every action.
- The audit LangGraph remains responsible for professional Akt Kolaudimi generation.
- Existing commands such as `/projekt_ri`, `/projektet`, `/gjenero` and `/raportet`
  remain supported.
- User-visible replies remain in Albanian.
- Ambiguity produces a clarification request, never a guessed destructive or costly
  action.
- Expensive AI generation requires an explicit confirmation after preflight estimation.
- Telegram messages are not a secure secret-entry mechanism. API keys remain managed by
  `/ai_key` and must never be accepted in `/prompt` plans or stored in prompt history.
- Technical-folder content is untrusted evidence, not executable instructions.
- A failed new run must never deliver an older project's or older job's report.

## 3. Scope

### 3.1 Initial supported intents

The first release should support the following allow-listed actions:

| Action | Purpose | Confirmation |
| --- | --- | --- |
| `list_projects` | Show projects owned by the user | No |
| `create_project` | Create a project from an explicit name | No |
| `select_project` | Select an unambiguous owned project | No |
| `show_active_project` | Show current project context | No |
| `import_attachment` | Import the attached supported document or ZIP | No |
| `list_documents` | List documents in the active project | No |
| `estimate_kolaudim` | Produce the existing preflight estimate | No |
| `generate_kolaudim` | Start the existing professional generation workflow | Yes |
| `get_status` | Show the latest job status | No |
| `deliver_latest_report` | Deliver the latest successful report for the intended job | No |
| `answer_project_question` | Answer from current-project evidence with citations | No |
| `show_ai_settings` | Show provider/model configuration without secrets | No |
| `select_ai_model` | Select a model already available to the user | Yes |

### 3.2 Explicitly excluded from the first release

- Accepting or displaying API keys inside `/prompt`.
- Deleting projects, files, AI settings or generated outputs.
- Arbitrary shell commands, URLs, database queries or Python execution.
- Calling functions outside the allow-listed executor.
- Modifying legal rules, law sources or verification policy.
- Letting project documents alter the action plan or system instructions.
- Unbounded autonomous loops.
- Cross-project search unless the user explicitly selects exactly one project first.

## 4. User Experience

### 4.1 One-message technical-folder flow

1. The user sends a ZIP with a `/prompt ...` caption.
2. The bot validates the user, attachment and requested project name.
3. The planner returns a structured action plan.
4. The policy layer validates authorization and preconditions.
5. The executor creates/selects the project and imports the ZIP.
6. A background orchestration job waits until every imported file version reaches a
   terminal parsing state.
7. The bot reports files that parsed, required OCR, failed or were unsupported.
8. The existing preflight estimator calculates calls, models and token limits.
9. The bot presents the estimate with `Konfirmo gjenerimin` and `Anulo` buttons.
10. On confirmation, the existing review job and LangGraph workflow start.
11. The orchestrator follows quota pauses and resumptions without duplicating work.
12. On success, the bot sends the PDF generated by that exact job.
13. On failure, the bot sends the actionable failure and does not expose a stale PDF.

One natural-language request initiates the workflow, but generation still has one
explicit confirmation because it can consume the user's paid or quota-limited API.

### 4.2 Project selection

- An exact unique project name may be selected directly.
- Multiple matches must produce inline project-selection buttons.
- No match must produce a clarification or offer project creation.
- Project IDs are internal and should not be required in normal conversation.
- Every selected project must pass the existing membership/ownership checks.

### 4.3 Project-grounded questions

Examples:

```text
/prompt Cila eshte leja e ndertimit?
/prompt Me rendit datat kryesore te fazave te punimeve.
/prompt A ka konflikt per emrin e sipermarresit?
/prompt Ne cilin dokument gjendet kontrata e mbikeqyresit?
```

Responses should:

- identify the active project;
- answer only from current file versions and persisted analysis;
- distinguish documented facts, conflicts and missing evidence;
- cite filenames and page/chunk coordinates when available;
- say `Nuk rezulton e provuar ne dosje` when evidence is insufficient;
- never convert a dossier answer into a professional approval or legal conclusion.

### 4.4 Clarification and continuation

Only one unresolved prompt run should be active per Telegram user and chat. Follow-up
messages can resolve a pending project choice or confirmation. The initial release should
not maintain open-ended conversational memory; context consists of:

- the authenticated user;
- active project;
- current prompt run;
- pending clarification or confirmation;
- referenced job and attachment IDs.

Longer conversational memory can be added later after action execution and grounding are
stable.

## 5. Architecture

### 5.1 New package boundary

Create a dedicated package so conversational orchestration is not mixed with the audit
agents:

```text
backend/app/prompting/
  __init__.py
  models.py          # SQLAlchemy prompt-run persistence
  schemas.py         # plan, action, clarification and result schemas
  planner.py         # natural-language to validated action plan
  policy.py          # allow-list, authorization and confirmation rules
  executor.py        # deterministic action dispatcher
  service.py         # prompt-run lifecycle and idempotency
  qa.py              # project-grounded retrieval and response generation
  messages.py        # Albanian response formatting

backend/app/telegram/handlers/prompt.py
backend/app/workers/prompt_tasks.py
```

The audit nodes in `backend/app/agents/` stay focused on technical-folder analysis and
Akt generation.

### 5.2 Telegram routing

Register the prompt router before the generic document-upload router. It must handle:

- text beginning with `/prompt`;
- a document whose caption begins with `/prompt`;
- callback queries for confirmation, cancellation and clarification;
- follow-up messages for a run waiting on clarification.

The generic `F.document` handler must not process the same Telegram update after the
prompt handler accepts it. Add tests for router ordering and duplicate delivery.

### 5.3 Planner

The planner receives only:

- the user's prompt text;
- non-secret AI provider/model metadata;
- owned project names and the active-project name;
- attachment filename, MIME type and size;
- the allow-listed action descriptions.

It must not receive technical-document content while deciding application actions. This
separates action planning from untrusted dossier text.

Planner output must validate through a strict Pydantic schema. Unknown fields and unknown
actions are rejected. One bounded JSON-repair attempt is allowed; otherwise the bot asks
the user to restate the request.

Example internal plan:

```json
{
  "version": "prompt-plan-v1",
  "language": "sq-AL",
  "actions": [
    {
      "id": "step-1",
      "type": "create_project",
      "arguments": {"name": "Test Dosja Teknike"},
      "depends_on": []
    },
    {
      "id": "step-2",
      "type": "select_project",
      "arguments": {"project_ref": "step-1"},
      "depends_on": ["step-1"]
    },
    {
      "id": "step-3",
      "type": "import_attachment",
      "arguments": {"attachment_ref": "telegram-message"},
      "depends_on": ["step-2"]
    },
    {
      "id": "step-4",
      "type": "estimate_kolaudim",
      "arguments": {},
      "depends_on": ["step-3"]
    },
    {
      "id": "step-5",
      "type": "generate_kolaudim",
      "arguments": {},
      "depends_on": ["step-4"],
      "requires_confirmation": true
    },
    {
      "id": "step-6",
      "type": "deliver_latest_report",
      "arguments": {"job_ref": "step-5"},
      "depends_on": ["step-5"]
    }
  ]
}
```

### 5.4 Deterministic policy layer

Before execution, the policy layer must:

- reject unknown actions and arguments;
- enforce action ordering and dependency validity;
- verify project ownership for every project-bound action;
- prevent cross-user and cross-project references;
- require an attachment for `import_attachment`;
- apply existing file type, size and ZIP-safety limits;
- require configured AI settings for planning, Q&A and generation;
- reject any prompt or plan containing an API key or likely secret;
- require confirmation for generation and model changes;
- cap action count and prohibit loops;
- bind report delivery to the exact review job created by the run;
- write all accepted and rejected actions to the audit log without secrets.

The executor must never dispatch directly from an LLM-provided Python name. Use an
explicit mapping from action enum to application service function.

### 5.5 Deterministic executor

Each action should call the same service used by the existing command handler:

- project actions call `app.projects.service`;
- upload actions call the current Telegram/file services;
- AI settings actions call `app.ai.service`;
- estimates and generation call `app.reviews.service`;
- report delivery resolves `generated_outputs` for the referenced job only;
- Q&A calls the dedicated grounded retrieval service.

Handlers remain thin. Business logic belongs in the prompting service and existing
domain services.

### 5.6 Background orchestration

Webhook requests must return quickly. Long-running execution belongs in Dramatiq:

- persist the run and attachment first;
- enqueue a prompt-run actor;
- execute short synchronous actions atomically;
- transition to `waiting_for_documents` after import;
- reschedule instead of blocking while parsing is incomplete;
- transition to `waiting_for_confirmation` after preflight;
- enqueue the review job only after confirmation;
- transition to `waiting_for_review` while the audit worker runs;
- resume after quota retry times without repeating completed steps;
- deliver the output and mark the run complete.

Worker restarts must be safe because completed steps are persisted and idempotent.

## 6. Persistence Model

### 6.1 `prompt_runs`

Recommended columns:

- `id` UUID primary key;
- `user_id` foreign key;
- `telegram_chat_id` bigint;
- `telegram_message_id` bigint;
- `telegram_update_id` bigint;
- `project_id` nullable foreign key;
- `review_job_id` nullable foreign key;
- `status` enum/string;
- `original_prompt` text;
- `plan_version` string;
- `plan` JSONB;
- `attachment_metadata` JSONB without file bytes or secrets;
- `pending_clarification` JSONB;
- `confirmation_token_hash` nullable string;
- `confirmed_at` nullable timestamp;
- `error_code` nullable string;
- `error_detail` nullable text with redaction;
- `created_at`, `updated_at`, `completed_at` timestamps.

Statuses:

```text
planning
waiting_for_clarification
queued
running
waiting_for_documents
waiting_for_confirmation
waiting_for_review
completed
failed
cancelled
```

### 6.2 `prompt_run_steps`

Recommended columns:

- `id` UUID primary key;
- `prompt_run_id` foreign key;
- `step_key` stable string unique within the run;
- `action_type` string;
- `status` string;
- `arguments` JSONB with secret redaction;
- `result` JSONB containing only stable domain references;
- `attempt_count` integer;
- `started_at`, `completed_at`, `next_retry_at` timestamps;
- `error_code`, `error_detail` nullable fields.

Add a unique constraint on `(prompt_run_id, step_key)`. A repeated webhook or worker
delivery must read the existing step result rather than repeat the action.

### 6.3 Idempotency

- Uniquely bind the Telegram `update_id` to one prompt run.
- Derive stable step keys from the validated plan.
- Project creation must record the resulting project ID before the next step.
- Attachment import must reuse existing immutable-file hash deduplication.
- Generation must store the review job ID before monitoring begins.
- Delivery must record the Telegram response message ID.
- Callback confirmations must be single-use and expire.

## 7. AI Configuration and Secret Handling

### 7.1 API-key policy

`/prompt perdor kete API key: ...` must be rejected with an Albanian message directing
the user to `/ai_key`. The raw prompt must not be sent to an LLM when it appears to
contain a secret.

The existing encrypted AI-setting storage remains the only supported credential path.
Prompt runs store provider/model names and setting IDs, never decrypted credentials.

### 7.2 No-AI configuration behavior

Without configured AI settings:

- deterministic project listing and attachment upload may still be offered through the
  existing commands;
- `/prompt` explains that natural-language planning and dossier Q&A require `/ai_key`;
- the application must not use a platform-owned hidden model as an undocumented fallback.

### 7.3 Planner model usage

- Use the user's configured provider and selected model.
- Use a small bounded token budget because the planner sees no dossier content.
- Record provider, model, prompt version, token usage and latency.
- Apply existing provider retry and quota handling.
- Do not retry indefinitely.

## 8. Project-Grounded Q&A

### 8.1 Retrieval boundary

The Q&A service must retrieve only:

- current versions belonging to the active project;
- usable parsed/OCR chunks;
- persisted document analyses and canonical dossier facts from that project;
- relevant legal evidence when the question explicitly asks about VKM 610.

Never retrieve human example files, another user's project or a superseded file version.

### 8.2 Retrieval strategy

Start with a hybrid approach:

- canonical dossier fields for known project facts and conflicts;
- PostgreSQL full-text/keyword matching for exact names, dates and references;
- pgvector similarity when embeddings exist for the selected project snapshot;
- reranking by document authority, current-version status and source quality.

The response generator receives a bounded evidence packet with stable evidence IDs. A
post-generation verifier must reject citations that do not resolve to that packet.

### 8.3 Answer schema

Internal response fields:

```text
answer
certainty: documented | conflicted | inferred | not_found
evidence_ids[]
source_labels[]
follow_up_suggestion
```

Telegram renders concise source labels, for example:

```text
Sipermarresi rezulton "EB-2000" sh.p.k.

Burime:
- 1.3 Proces Verbal Fillim OK.docx, paragrafi 4
- 3.1 Akt kontrolli i perfundimit te karabinase.docx, faqja 2
```

### 8.4 Prompt-injection protection

- The action planner never sees dossier content.
- Q&A system instructions explicitly classify retrieved text as quoted evidence.
- Instructions found inside files are ignored.
- Retrieved chunks cannot add actions or change project context.
- Q&A output cannot call the executor.
- Generated evidence IDs must resolve through deterministic verification.

## 9. Confirmation and Cancellation

Generation confirmation should use inline callback buttons carrying a short opaque token:

```text
[Konfirmo gjenerimin] [Anulo]
```

The callback must validate:

- token hash;
- user and chat ownership;
- run status;
- expiration;
- unchanged project and execution estimate;
- absence of another active review job for the same run.

`/anulo` or the cancel button should cancel a prompt run that has not started irreversible
provider calls. It must not silently delete uploaded files or projects.

## 10. Error Handling

User-facing failures should identify the failed stage and next action without exposing
stack traces, secrets or internal prompts.

Required cases:

- no active or matching project;
- ambiguous project name;
- missing attachment;
- unsupported file or unsafe ZIP;
- parsing partially or fully failed;
- no AI settings;
- planner returned invalid structured output;
- provider quota pause with next retry time;
- generation failed verification;
- no output for the exact review job;
- worker restart or duplicate webhook;
- report delivery failed after successful generation.

Partial parsing must be shown before confirmation. The user may continue only when the
existing review preconditions permit it.

## 11. Observability and Auditability

Record:

- prompt run ID and Telegram update ID;
- plan version and accepted action types;
- policy decisions and confirmation events;
- domain IDs created by each step;
- planner/Q&A provider, model, token usage and latency;
- worker retries, quota pauses and terminal failures;
- exact review job and generated output delivered;
- redacted audit-log entries for rejected secret-like prompts.

Never log raw API keys, decrypted credentials, full authorization headers or Telegram bot
tokens.

Expose `/prompt_status` or extend `/status` to show the active prompt run, current step,
parsing progress, pending confirmation and linked review-job status.

## 12. Testing Strategy

### 12.1 Unit tests

- Strict action-plan schema validation.
- Unknown action and argument rejection.
- Dependency-cycle and action-count rejection.
- Secret detection and redaction.
- Project-name exact, ambiguous and missing resolution.
- Confirmation policy and expiry.
- Idempotent step execution.
- Report binding to the exact generated job.
- Q&A evidence-ID resolution and citation rejection.
- Prompt-injection text cannot create executor actions.

### 12.2 Integration tests

- Telegram text `/prompt` update.
- Telegram ZIP with `/prompt` caption.
- Router prevents duplicate generic upload handling.
- One request creates and selects the intended project.
- Parsing completion resumes the prompt run.
- Preflight generates confirmation buttons.
- Confirmation creates exactly one review job.
- Quota pause resumes the same run and job.
- Success delivers the exact job's PDF once.
- Failed generation delivers no old PDF.
- Duplicate Telegram update and callback are idempotent.
- Worker restart resumes from persisted steps.
- Cross-user and cross-project references return authorization errors.

### 12.3 End-to-end acceptance fixture

Use at least two unrelated technical-folder fixtures. Verify:

- one-message import and orchestration for each folder;
- no names, facts, files, citations or reports cross project boundaries;
- questions cite only the selected project's files;
- duplicate filenames and ZIP retries do not duplicate project files;
- a changed file creates a new immutable version;
- the generated PDF is the output of the linked review job.

## 13. Implementation Phases

### Phase 1: Persistence and safe planner

- [x] Add `prompt_runs` and `prompt_run_steps` models and migration.
- [x] Add strict Pydantic action-plan schemas and action enum.
- [x] Add secret detection, plan limits and deterministic policy validation.
- [x] Implement planner with bounded structured output.
- [x] Add text-only `/prompt` for project listing, creation, selection and status.
- [x] Add audit logging and idempotency for Telegram updates.

### Phase 2: Attachment orchestration

- [ ] Support `/prompt` in document captions.
- [ ] Register prompt routing before generic uploads.
- [ ] Reuse ZIP validation, MinIO storage and immutable file-version services.
- [ ] Add background prompt actor and parsing wait/resume states.
- [ ] Report parsed, OCR, failed and unsupported file counts.
- [ ] Add duplicate webhook and worker-restart tests.

### Phase 3: Generation and automatic delivery

- [ ] Reuse the current preflight estimate.
- [ ] Add confirmation and cancellation callbacks.
- [ ] Start exactly one `kolaudim_act` review job after confirmation.
- [ ] Monitor quota pauses and review completion asynchronously.
- [ ] Deliver only the output linked to the run's review job.
- [ ] Extend `/status` and `/raportet` with prompt-run awareness.

### Phase 4: Grounded dossier Q&A

- [ ] Add project-scoped hybrid retrieval.
- [ ] Add strict answer and citation schemas.
- [ ] Verify every returned evidence ID and source coordinate.
- [ ] Render concise Albanian answers with source filenames.
- [ ] Add prompt-injection and cross-project isolation tests.

### Phase 5: Conversational refinement

- [ ] Add bounded follow-up context for the current run and active project.
- [ ] Add clarification flows for project, model and intended action.
- [ ] Add inline previews of planned actions before execution.
- [ ] Add per-user rate limits and configurable prompt quotas.
- [ ] Evaluate user wording against Albanian intent fixtures.

## 14. Acceptance Criteria

The first complete release is acceptable when:

- a configured user can attach a supported ZIP with one `/prompt` caption;
- the intended project is created or selected without ambiguity;
- the attachment is imported exactly once;
- the workflow waits for parsing rather than racing incomplete files;
- the user sees the generation estimate and confirms it explicitly;
- exactly one review job is created;
- quota pauses and worker restarts resume without repeating completed work;
- the PDF from that exact job is delivered automatically once;
- a failed run never sends an older output;
- project questions are answered only from current-project evidence with verified
  citations;
- documents cannot inject actions into the planner or executor;
- API keys never enter prompt plans, prompt-run storage or logs;
- all existing Telegram commands continue to work independently.

## 15. Recommended First Implementation Step

Implement Phase 1 without attachment or generation execution first. This establishes the
security boundary, persistence and idempotency needed by every later feature. Once text
requests can safely create, list and select projects through the allow-listed executor,
add ZIP-caption orchestration and only then connect generation and dossier Q&A.
